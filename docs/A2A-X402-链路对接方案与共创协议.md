## 1. 当前实现与目标架构

### 1.1 当前已实现

当前仓库已经实现：

- Injective EVM testnet：`eip155:1439`
- 自部署 mUSDC：ERC-20 + EIP-3009
- 买方对 `TransferWithAuthorization` 做 EIP-712 离线签名
- facilitator 代付 INJ gas，调用 `transferWithAuthorization`
- mUSDC 从买方地址直接转到卖方地址
- EIP-3009 nonce 链上防重放
- TypeScript `MockSettlement` 和 `RealSettlement`
- facilitator 的 `/health`、`/verify`、`/settle`、`/faucet`

当前主路径是：

```text
Agreement
  -> 生成 PaymentAuthorization
  -> SettlementSDK.lockFunds()
  -> SettlementSDK.settleTrade()
  -> POST /settle
  -> mUSDC.transferWithAuthorization()
  -> 链上确认
```

这里的 `lockFunds()` 只记录一笔本地待结算意图，不会在链上锁定资金。
返回的 `escrowId` 只是兼容旧接口的本地标识，不代表存在链上 escrow。

### 1.2 当前未实现或不保证

当前实现不提供以下保证：

- 没有完整的 HTTP `402 Payment Required` 资源服务器闭环
- 没有标准 x402 客户端重试和协议头处理
- 没有链上 escrow、条件释放或真实退款
- 没有实际收取平台手续费
- 没有持久化幂等存储
- 没有 TEE 私钥保护或 remote attestation 保证
- 没有 ERC-8004 链上注册和验证
- 没有生产级密钥管理、安全审计或主网资金保护
- Python `IPaymentGateway` 没有连接 `RealSettlement` 的真实适配器

`RealSettlement.refund()` 目前只是修改本地状态，不会退回链上资金，
也不会保证取消已经签出的 EIP-3009 authorization。当前实现还没有检查
原状态是否已经 `settled`，因此它甚至可能把一笔已经完成链上转账的本地状态
改写成 `refunded`；该状态不能作为退款或资金回退证明。

### 1.3 HTTP x402 目标架构

目标闭环是：

```text
Buyer Agent -> Resource Server: 请求资源
Resource Server -> Buyer Agent: 402 + protocol-defined payment requirements
Buyer Agent: 生成支付授权
Buyer Agent -> Resource Server: 按当前 x402 版本重试请求
Resource Server -> Facilitator: verify / settle
Facilitator -> Injective EVM: 提交支付并等待确认
Resource Server: 验证结算收据
Resource Server -> Buyer Agent: 交付资源
```

协议头名称、编码和版本必须来自已固定版本的官方 x402 库或规范。
本文不定义自造的 `X-402-*` 头，也不把当前 JSON `/verify`、`/settle`
端点描述为完整 x402 server。

## 2. 网络、地址和金额

### 2.1 网络与资产

| 字段 | 当前值 |
|---|---|
| CAIP-2 network | `eip155:1439` |
| EVM chain ID | `1439` |
| 地址格式 | `0x` EVM address |
| 当前资产 | `mUSDC` |
| decimals | `6` |
| 当前 token 地址 | `0x06D223D12774386A96D33863D9106A800e52BDeD` |

token 地址和 decimals 必须从 `deployments.json` 读取。
上表只是 Last verified 时的快照。

禁止在当前 EVM 结算路径中使用 Cosmos chain ID `injective-1`
或 `inj1...` 地址。

### 2.2 金额表示

结算权威金额必须使用最小单位：

- TypeScript：`bigint`，跨 JSON 边界时使用十进制字符串
- Python：`int` 或十进制字符串
- 示例：`1.6 mUSDC` 表示为 `"1600000"`

禁止使用 `float` 作为签名、结算、比较、幂等或收据验证的权威金额。
UI 可以展示小数，但必须由 `amountAtomic` 和 token decimals 派生。

当前 `SettlementSDK.lockFunds()` 仍保留 `amount: number`。
这是旧接口兼容字段，只能用于显示或旧返回值计算；
真实链上转账金额以 `PaymentAuthorization.value` 为准。

## 3. 标识符与幂等

所有跨模块请求必须携带以下标识：

| 字段 | 含义 | 生命周期 |
|---|---|---|
| `orderId` | A2A 侧准备结算的规范化订单 ID | 订单创建后不变 |
| `dealId` | 买卖双方接受条款后生成的不可变成交 ID | 一次成交一个 |
| `paymentId` | 一次经济支付意图的 ID | 网络重试时保持不变 |
| `idempotencyKey` | 该支付操作的幂等键 | 同一 `paymentId` 的重试保持不变 |

规则：

1. `dealId` 对应当前 SDK 的 `negotiationId`。
2. 一个 `dealId` 可以有多个支付目的，但每一笔独立支付必须使用新的 `paymentId`。
3. 传输超时、HTTP 重试或进程重启不能生成新的 `paymentId`。
4. 相同 `idempotencyKey` 必须对应完全相同的 network、asset、from、to 和 amount。
5. 如果相同幂等键收到不同 payload，必须返回冲突错误，不能尝试结算。
6. EIP-3009 `nonce` 标识一次授权尝试；不同授权不得复用 nonce。
7. authorization 过期后重新签名时，`paymentId` 和 `idempotencyKey` 保持不变，
   但必须使用新 nonce。

当前 facilitator 不读取也不持久化 `idempotencyKey`。
在补齐服务端幂等存储前，A2A/Settlement 适配层必须负责去重并串行化同一笔支付。

## 4. 跨模块数据契约

以下 DTO 是目标集成契约。当前仓库尚未完整实现这个 envelope。

```typescript
type EvmAddress = `0x${string}`;
type AtomicAmount = `${bigint}`;

interface SettlementCommand {
  orderId: string;
  dealId: string;
  paymentId: string;
  idempotencyKey: string;

  network: "eip155:1439";
  asset: EvmAddress;
  amountAtomic: AtomicAmount;
  payerAddress: EvmAddress;
  payeeAddress: EvmAddress;

  authorization: PaymentAuthorization;
  expiresAt: number; // Unix seconds
}

interface PaymentAuthorization {
  from: EvmAddress;
  to: EvmAddress;
  value: AtomicAmount;
  validAfter: AtomicAmount;
  validBefore: AtomicAmount;
  nonce: `0x${string}`; // exactly 32 bytes
  v: number;
  r: `0x${string}`;
  s: `0x${string}`;
  token: EvmAddress;
  chainId: 1439;
}
```

适配层在调用 Settlement 前必须验证：

- `network === "eip155:1439"`
- `authorization.chainId === 1439`
- `asset === authorization.token === deployments.usdc.address`
- `payerAddress === authorization.from`
- `payeeAddress === authorization.to`
- `amountAtomic === authorization.value`
- 所有地址都是合法 `0x` EVM 地址
- `amountAtomic` 是大于零的十进制整数字符串
- nonce 是 32 字节且未用于另一笔授权
- 当前时间满足 `validAfter < now < validBefore`
- `expiresAt` 与 authorization 的有效期一致
- EIP-712 domain 与当前 deployments 一致
- 签名恢复地址等于 `authorization.from`

任一检查失败都不得进入 `/settle`。

## 5. 当前 TypeScript SettlementSDK

当前可用实现：

```typescript
import {
  MockSettlement,
  RealSettlement,
  type SettlementSDK,
  type PaymentAuthorization,
} from "@agent-arena/settlement-sdk";
```

现有 API：

```typescript
const { escrowId } = await settlement.lockFunds({
  negotiationId: dealId,
  buyerWallet: payerAddress,
  sellerWallet: payeeAddress,
  amount: amountDisplayForLegacySdkOnly,
  currency: "USDC",
  x402Signature: JSON.stringify(authorization),
  expiry: expiresAtMilliseconds,
});

const result = await settlement.settleTrade({ escrowId });
```

注意：

- 上例的 `amountDisplayForLegacySdkOnly` 不是结算权威。
- 适配层必须先用 `BigInt(authorization.value)` 完成金额和字段校验。
- `lockFunds()` 返回成功只表示本地记录成功，不表示资金已锁定或支付已完成。
- 只有链上交易成功且收据验证通过后，才能产生 `SETTLED`。
- 当前 `platformFee` 和 `amountToSeller` 返回值不能作为实际扣费证明；
  facilitator 当前把 authorization 的完整 `value` 转给 `to`。

| 旧 Python 字段 | 新契约 |

## 7. 支付状态

跨模块状态使用以下语义：

| 状态 | 含义 | 是否允许交付 |
|---|---|---|
| `CREATED` | 已创建支付意图，尚未签名 | 否 |
| `AUTHORIZED` | 已生成并校验 authorization | 否 |
| `PRECHECK_PASSED` | 当前 `/verify` 预检通过 | 否 |
| `SETTLING` | 已提交或正在确认，结果未知 | 否 |
| `SETTLED` | 链上成功且收据字段匹配 | 是 |
| `FAILED_RETRYABLE` | 网络、RPC 或确认暂时失败 | 否 |
| `FAILED_FINAL` | 签名、字段、余额或链上执行确定失败 | 否 |
| `EXPIRED` | authorization 已过期 | 否 |
| `CANCELLED_LOCAL` | 本地取消；不代表链上退款或授权已撤销 | 否 |

当前 SDK 状态映射：

| 当前值 | 集成层含义 |
|---|---|
| `lockFunds().status === "locked"` | `AUTHORIZED`，不是 escrow locked |
| `/verify { ok: true }` | `PRECHECK_PASSED` |
| `/settle` 已提交但未确认 | `SETTLING` |
| `/settle` 成功且收据验证通过 | `SETTLED` |
| `refund().status === "refunded"` | `CANCELLED_LOCAL` |

## 8. `/verify` 的实际限制

当前 facilitator `/verify` 只检查：

- `validBefore` 尚未过期
- EIP-3009 nonce 在 token 合约中尚未使用
- `from` 地址的 token 余额不小于 `value`

它当前不检查：

- EIP-712 签名是否合法
- `validAfter`
- `chainId === 1439`
- token 是否为 deployments 中允许的 mUSDC
- from、to、value 是否与 deal 和 SettlementCommand 一致
- `paymentId` 或 `idempotencyKey`
- 已存在的成功交易或业务级重复支付

因此 `/verify { ok: true }` 不是支付证明，也不能触发交付。
链上 token 合约会在 `/settle` 时验证签名和授权时间，
但业务字段一致性仍必须由适配层提前验证。

## 9. 失败、重试与对账

### 9.1 可重试

以下错误可进入 `FAILED_RETRYABLE`：

- HTTP 连接失败
- RPC 暂时不可用
- 等待确认超时
- 已提交交易但本地未取得最终结果

重试前必须先按 `paymentId`、nonce 和 tx hash 对账：

1. 检查本地是否已有 `SETTLED` 收据。
2. 检查 nonce 是否已在链上使用。
3. 如果 nonce 已使用，定位对应交易并验证 transfer。
4. 只有确认尚未结算后，才允许用同一 payload 重试。
5. 不得因超时直接生成新的 `paymentId` 或再次付款。

### 9.2 不可盲目重试

以下错误应进入 `FAILED_FINAL` 或要求重新签名：

- 签名恢复地址不匹配
- network、token、from、to 或 amount 不匹配
- 余额不足
- authorization 已过期
- authorization 尚未生效
- nonce 已用于另一笔交易
- 链上交易确定 revert
- 收据中的 token transfer 与预期不一致

authorization 过期后可以在同一 `paymentId` 下重新签名，
但必须使用新 nonce，并保留旧 authorization 的审计记录。

## 10. 交付门控

Seller/Resource Server 必须满足全部条件后才能交付最终资源：

1. `dealId`、`orderId` 和 `paymentId` 与待交付订单匹配。
2. 状态为 `SETTLED`。
3. 交易在 `eip155:1439` 成功确认。
4. token 地址与当前 deployments 一致。
5. transfer 的 from、to 和原子金额与 SettlementCommand 完全一致。
6. nonce 对应该笔 authorization。
7. 同一 `paymentId` 尚未触发过最终交付。

以下内容都不足以触发交付：

- A2A 消息中存在 proof 字段
- `lockFunds()` 返回 `locked`
- `/verify` 返回 `{ ok: true }`
- 收到 tx hash 但没有确认和字段验证
- 本地 mock 返回成功
- `CANCELLED_LOCAL` 或 `refunded`

交付操作必须以 `paymentId` 或 `dealId` 做幂等保护。
重复收到同一结算确认时，返回同一交付结果，不得重复执行不可逆交付。

## 11. 安全边界

- 私钥、助记词和签名密钥不得出现在仓库、日志、A2A 消息或错误响应中。
- 当前测试密钥和 `LocalAccount` 使用方式不构成 TEE 保证。
- facilitator 是当前 gas 赞助者和交易提交者，不是 escrow 托管方。
- mUSDC 是测试网 mock 资产，不得描述为主网 USDC。
- `escrowId`、`refund`、`platformFee` 等旧接口名称不等于链上已有对应能力。
- 对未知支付结果采用 fail closed：保持不交付，先对账。
- 金额、地址、网络和 token 校验失败时不得自动纠正后继续支付。

## 12. 集成完成标准

### A2A/Matching

- [ ] 在成交时生成稳定的 `orderId`、`dealId`、`paymentId` 和 `idempotencyKey`
- [ ] 使用 `0x` EVM 地址和 `eip155:1439`
- [ ] 使用原子单位整数，不用 float 作为权威金额
- [ ] 实现 Python 到 TypeScript Settlement 的真实适配器
- [ ] 持久化支付状态和幂等记录
- [ ] 只有 `SETTLED` 可以触发交付
- [ ] 重复确认不会重复交付

### Settlement

- [ ] 校验 authorization 与 SettlementCommand 的所有绑定字段
- [ ] 为 `/verify` 增加签名、domain、network、token、to 和 amount 校验
- [ ] 增加持久化 `paymentId` / `idempotencyKey` 去重
- [ ] 返回可独立验证的标准结算收据
- [ ] 修正或移除当前未实际扣取的 fee 返回语义
- [ ] 明确取消 authorization 的实现；不能把本地 `refund` 当链上退款

### HTTP x402 目标路径

- [ ] 固定并记录 x402 库和协议版本
- [ ] Resource Server 返回该版本定义的标准 payment requirements
- [ ] Client 按该版本完成签名和请求重试
- [ ] Server 在交付前完成 verify、settle 和收据校验
- [ ] 不再依赖自定义 `X-402-*` 头
- [ ] 用 `eip155:1439` 和当前 testnet asset 完成真实集成测试

### 必测场景

- [ ] Happy path：授权、结算、确认、交付
- [ ] 相同幂等键重复请求只支付一次
- [ ] 同一 nonce 重放被拒
- [ ] 超时但实际上链成功时能够对账，不重复支付
- [ ] from、to、amount、token、chain 任一不匹配时失败关闭
- [ ] 余额不足和 authorization 过期时不交付
- [ ] 重复结算确认只交付一次
- [ ] mock 与真实 Settlement 的状态映射一致
